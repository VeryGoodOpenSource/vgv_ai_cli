# Claude Code Setup for vgv_ai_cli

## What We're Building

A committed, team-wide Claude Code configuration for developing `vgv_ai_cli` itself, built on the two VGV plugins already in use: `vgv-wingspan` (lifecycle workflows) and `vgv-ai-flutter-plugin` (Dart/Flutter standards and quality gates). The setup is configuration only — no custom hooks and no repo-local skills.

Scope is this repository's own development experience. What the `vgv_ai` CLI eventually scaffolds into other projects is a separate conversation and explicitly out of scope here.

## Why This Approach

Three approaches were considered: a thin config-only layer, that layer plus a `PreToolUse` hook guarding the generated `lib/src/version.dart`, and a full custom layer adding repo-local release and command-scaffold skills.

Thin was chosen. The two plugins already cover this repo's language, quality gates, and workflow, so almost everything needed is wiring rather than new code. Config has no maintenance cost as the plugins version up, whereas custom hooks and skills do. The custom skills in particular would automate rituals this repo has not yet performed — it sits at version `0.0.1` with two commands, and Wingspan's `/build` plus `green-gate` already cover most of the ground.

## Key Decisions

- **Scope limited to this repo's development setup.** The repo's stated purpose is configuring AI agents, which makes "what should the CLI generate" a tempting adjacent question. Keeping it out keeps this shippable.

- **Configuration is committed, not local.** `.claude/settings.json` goes in version control so every contributor gets the same permissions and plugin expectations. This raises a distribution problem to solve during planning, noted under Open Questions.

- **Full workflow autonomy in the permissions allowlist.** Pre-approve inspection, quality gates, local writes, push, and `gh pr create`, so `/build` can run end-to-end unattended.

- **Pair that autonomy with an explicit `deny` list.** Force-push and pushes to `main` stay blocked. A committed allowlist applies to contributors who never opted into it, so the irreversible edges should remain guarded even though the everyday path is unattended.

- **Rewrite the CLAUDE.md command guidance.** The flutter plugin's `block-cli-workarounds.sh` hook denies `dart test`, `very_good test`, and `flutter test` when run through Bash, redirecting to the `very_good_cli` MCP `test` tool. The CLAUDE.md written before this brainstorm documents `dart test ...` as the way to run tests, which fails the moment the plugin is active. The same applies to running a single test.

- **Document the plugin hooks' side effects and their `jq` dependency.** The flutter plugin runs `dart analyze` and `dart format` automatically on every `.dart` Edit or Write, and several hooks across both plugins skip or fail without `jq` installed.

- **Steer toward the Dart-relevant subset of flutter plugin skills.** This is a pure Dart CLI. Roughly ten of the plugin's fifteen skills — bloc, accessibility, material-theming, navigation, animations, internationalization, ui-package among them — never apply. The ones that do: `green-gate`, `testing`, `license-compliance`, `very-good-analysis-upgrade`, `dart-flutter-sdk-upgrade`.

- **Create the `docs/` directories Wingspan expects and gitignore the ephemeral ones.** Wingspan writes to `docs/brainstorm/`, `docs/plan/`, `docs/reviews/`, `docs/code-review/`, and `docs/debriefs/`. Reviews are ephemeral and cleaned up by the skills that produce them; brainstorms and plans are durable artifacts worth committing.

- **No custom hooks.** The `lib/src/version.dart` guard was considered and deliberately deferred. The file is generated by `build_version` and hand-editing it fails the `verify-version` CI job, so the failure mode is real but caught, just later than ideal.

- **No repo-local skills.** Release and command-scaffold skills are deferred until the underlying rituals have been performed manually enough times to know what they should encode.

## Open Questions

- **How do teammates resolve the VGV marketplace?** It is currently registered on this machine as a `directory` source pointing at a local worktree path. A committed `enabledPlugins` entry referencing `@very-good-claude-code-marketplace` will not resolve for anyone who has not added the marketplace themselves, and will resolve differently for anyone who added it from GitHub. Planning needs to settle whether to reference the public `VeryGoodOpenSource/very-good-claude-code-marketplace` repo, document a manual install step in the README, or both.

- **Should plugin versions be pinned?** Wingspan `0.0.4` and the flutter plugin `0.0.5` are both pre-1.0 and moving. Pinning gives reproducibility; floating gives fixes for free. Related: the flutter plugin's own recommendation file refers to itself as `very-good-ai-flutter-plugin` while it installs as `vgv-ai-flutter-plugin`, so exact identifiers need verifying rather than assuming.

- **Does the `deny` list cover the right things?** Force-push and pushes to `main` are the agreed baseline. Whether to also deny destructive git operations such as `git reset --hard` or branch deletion is unresolved.

- **Should the local SDK mismatch be addressed here or separately?** The package requires Dart `^3.13.0` and CI pins `3.13.0`, but the local toolchain is `3.12.1`, which blocks `dart pub get`. The code already uses 3.13 syntax. This is adjacent to the Claude setup rather than part of it, but it will block anyone verifying the setup works.
